# Estimation Breakdown

```text
Break this feature into tasks that I can estimate. Show the items that will
control the timeline.

Rules:
- Make each task 2 days or less. If a task is larger, split it or mark it as
  "spike needed."
- Include the work that teams frequently forget: migrations with rollback,
  config for each environment, test data, monitoring and alerts, docs and
  runbook, code review cycles, and deployment coordination.
- For each task: give an estimate range (best/likely) and a confidence level
  (H/M/L). If the confidence is low, give the reason ("depends on unknown
  vendor API behavior").
- List the assumptions behind the estimate. Each assumption is a risk with a
  cost if it is wrong.
- End with the critical path, the largest unknown risk, and the cheapest
  spike that will decrease that risk.
- Do not compress the ranges to please a person. An honest range of 3 to 6
  days is better than a hopeful 2 days.

The feature / ticket:
<<<paste the ticket, the notes, or the description. Include the tech stack
and the team size>>>
```
